## 1. 问题定义

### 1.1 输入

| 符号 | 含义 |
|---|---|
| $C = \{c_1, \dots, c_K\}$ | 容器集合（胸挂 + 背包），$K \le 2$，**按优先级有序** |
| $R_k$ | 容器 $k$ 的**可用格位图**：$W_k \times H_k$ 的 0/1 掩码，**非矩形** |
| $I$ | 候选物品（鱼款式）集合，$|I| \le 63$ |
| $w_i, h_i, v_i$ | 物品 $i$ 的宽、高、售价 |
| $n_i \in \mathbb{N} \cup \{\infty\}$ | 物品 $i$ 的可用数量（有限＝实际钓到数；$\infty$＝不限供给） |
| $\text{rot}$ | 是否允许 90° 旋转 |

**关键点 1：容器不是矩形，是格位图。**
真实胸挂是「两条竖带 + 中间白缝」这种形状，格位图中有洞。一件 2×2 的物品**不能跨过白缝**。
所以建模必须基于掩码，而不是 $W \times H$ 的连续矩形。

**关键点 2：尺寸是整数格，不是浮点。**

**关键点 3：容器按序填充**（先胸挂后背包）。这来自业务语义（胸挂先装小件），
也因此解空间按容器切分：每个容器独立求解，前一个容器的消耗传递到下一个。

### 1.2 输出

$$\max \sum_{i \in I} v_i \cdot \text{cnt}_i$$

约束：

1. $0 \le \text{cnt}_i \le n_i$（数量约束）
2. 每个容器 $k$ 内，所有放置的矩形互不重叠、且完全落在 $R_k$ 的可用格内
3. 每个物品实例至多放置一次

并要求返回**具体坐标**（谁放在哪个容器的哪一格、是否旋转），供 UI 绘制。

### 1.3 需要回答的三个业务问题

| # | 问题 | 求解方式 | 可信度 |
|---|---|---|---|
| ① | 本次钓获最多能带走多少价值？ | **有限供给**装箱 `report_catch()` | ✅ 精确（见 §7.1） |
| ② | 这一趟的收益天花板是多少？ | **不限供给**装箱 `plan_run().ceiling` | ⚠️ 默认预算内常为次优（§9.2） |
| ③ | 回本最少需要几条什么鱼？ | 按价值 DP + 装箱复核 `plan_run().break_even` | ⚠️ 不严格（§9.3） |

## 2. 为什么不用 CP-SAT / MILP

审计参考意见建议用 Google OR-Tools CP-SAT。**方向完全正确** —— 这确实是最适合的建模方式。
本实现没用它，原因如实列出：

1. **本机无依赖**：目标环境只有标准库。引入 OR-Tools 需联网安装（Windows wheel 体积大），
   而项目要求「双击即可运行」。
2. **有限供给规模可接受**：容器容量 ≤ 69 格，候选款式 ≤ 63 个。这个量级上，
   带记忆化的精确 DFS 足够用（有限供给场景毫秒级）。
3. **可解释性**：DFS 的搜索过程可以直接对应「空格子怎么填」，便于在白板上论证正确性。

**如果审计结论认为应迁移 CP-SAT，我不反对** —— 它确实能把「不限供给」从指数级降到可接受。
§10 列出了迁移时必须保持的语义。

### 2.1 与 CP-SAT 模型的对应关系

| CP-SAT 概念 | 本实现对应物 |
|---|---|
| `selected[i]` 0/1 变量 | DFS 分支：在锚点格上是否放某件物品 |
| `x[i], y[i]` 坐标变量 | 锚点格坐标 + 分支时枚举的偏移 |
| `rotation[i]` | 预生成两个朝向的 `_Shape`，作为独立候选 |
| `AddNoOverlap2D()` | 位掩码 `placed & occ == 0` |
| `AddAllowedAssignments()` | 容器掩码检查 `placed & ~region.mask == 0` |
| 数量约束 $\sum \text{selected} \le n_i$ | `rem[fish_index]` 递减计数 |
| `Maximize(Σ value)` | DFS 取 `max` |

**一个必须指出的技术细节**（参考意见里的 NoOverlap 写法会踩坑）：
把「A 在 B 左／右／上／下」写成四个**析取**约束时，若在选项内再乘上
`selected_A AND selected_B`，会得到 **bilinear（双线性）** 项，
而 CP-SAT 不能把 `Bool * Bool` 当作普通线性约束使用。

**但这不代表 CP-SAT 做不到这件事**：它有 `OnlyEnforceIf`、辅助布尔变量、
以及**可选区间（optional intervals, presence literal）** 等机制。
正确的迁移写法是把「是否选择这个位置」编码成布尔/可选区间，
再交给 `AddNoOverlap2D` 之类约束处理 —— 例如
`place[i][x][y][r]` 布尔变量 + 「覆盖同一格的所有位置至多选一个」。

本实现的分支结构天然避免了这个问题，因为「是否选中」与「放哪里」是同一个分支。

## 3. 算法主体：填最左上空格的分支限界

### 3.1 核心引理

> **引理（填充序完备性）**
> 设 $P$ 是任意一个合法的放置方案。设 $a$ 是格位图中**最左上**的空闲格
> （行优先扫描遇到的第一个未被 $P$ 覆盖的可用格）。
> 则 $a$ 要么在 $P$ 中为空，要么**恰好被 $P$ 中某一个矩形覆盖**。

**证明**：$a$ 是空闲格。若 $P$ 覆盖了 $a$，则覆盖它的矩形 $Q$ 必然包含 $a$。
$Q$ 的左上角 $(x_0, y_0)$ 满足 $x_0 \le a_x$ 且 $y_0 \le a_y$，
否则 $Q$ 会有比 $a$ 更左上的格子，与 $a$ 最左上矛盾。∎

**推论**：对 $a$ 的两种处理（留空／被某矩形以某个偏移覆盖）穷举，即可枚举出所有合法方案。
因此搜索是**完备**的 —— 不遗漏任何可行解，从而在搜索跑完时保证最优性。$\blacksquare$

这条引理是整套算法正确性的**全部依据**。审计请重点验证它（§7.1 给了对拍实验）。

### 3.2 状态表示

```python
solve(ri: int, occ: int, rem: tuple[int, ...]) -> (value, counts)
```

| 参数 | 含义 |
|---|---|
| `ri` | 当前处理到第几个容器 |
| `occ` | 当前容器已占格位图，**Python 任意精度整数位掩码**，bit $i$ ↔ 格 $(i \bmod W, \lfloor i/W \rfloor)$ |
| `rem` | **按鱼种**（非按朝向）的剩余数量元组 |

> **为什么按鱼种而不是按朝向**：同一鱼种的两个朝向如果各自计数，
> 会产生大量等价状态（先放横的再放竖的 ＝ 先放竖的再放横的），记忆化命中率骤降。
> 按鱼种计数消除了这个对称性。

### 3.3 掩码表示的**关键陷阱**（曾导致真实 bug）

矩形的相对掩码**依赖目标网格的行宽**。

一个 1×3 的矩形，在**宽度为 2** 的网格里占位是 bit $\{0,2,4\}$（每行一个，折行），
在**宽度为 3** 的网格里才是 bit $\{0,1,2\}$。

早期版本用 `(1 << (w*h)) - 1` 预计算掩码，然后在旋转后复用，
导致 3×1 与 1×3 共用同一个错误掩码 —— **旋转后的矩形折行**，最优解被静默漏掉。
这个 bug 是**靠暴力对拍实验抓出来的**，肉眼看代码看不出来。

修复方式：不预存掩码，改为存**相对坐标元组**，在放置时现场生成：

```python
@dataclass(frozen=True, slots=True)
class _Shape:
    cells_xy: tuple[tuple[int, int], ...]   # ((dx, dy), ...)

    def place(self, shift: int, region_w: int) -> int:
        mask = 0
        for dx, dy in self.cells_xy:
            mask |= 1 << (shift + dy * region_w + dx)
        return mask
```

**审计建议**：这是我认为最容易再次出错的点。请专门构造 `region_w < shape_w` 的用例
（例如 2 格宽的容器 + 3×1 的鱼）。§7.3 有现成用例。

### 3.4 分支：枚举覆盖锚点的所有方式

```python
a        = 最左上空闲格（free & -free 取最低位）
ax, ay   = a 的坐标

# 分支 1：留空
solve(ri, occ | (1 << a), rem)

# 分支 2：物品 v 覆盖 a
for v in variants:
    if rem[v.fish_index] == 0 or v.cells > free_cells: continue
    for x0 in range(ax, ax - v.w, -1):        # v 的左上角必须在 a 的左上方
        for y0 in range(ay, ay - v.h, -1):
            place = v.place(y0*W + x0, W)
            if place & ~rmask or place & occ: continue    # 越界 / 重叠
            solve(ri, occ | place, rem - e_v)
```

**「留空」分支是必需的**：它让算法可以选择不用这个格子，
从而覆盖「最优解不填满容器」的情况（例如格子数不被任何鱼尺寸整除）。

偏移枚举范围 $x_0 \in [a_x-w+1, a_x]$、$y_0 \in [a_y-h+1, a_y]$ 恰好是
**所有能让矩形覆盖到 $a$ 的位置**。范围外的位置不覆盖 $a$，由引理可知无需考虑。

### 3.5 容器推进

```python
if free == 0:                      # 本容器填满 → 进入下一个容器
    return solve(ri + 1, 0, rem)
if ri >= len(regions):             # 没有容器了 → 终止
    return gained
```

`occ` 在推进时归零，因为掩码是**容器局部**的。

> ⚠️ **这里曾有一个致命错误**：早期版本在填入目标函数（`gained`）之后，
> 把这一段写成了 `if free_n == 0: return gained` —— 也就是**直接收工**，
> 而不是推进到下一个容器。后果是搜索在"第一个容器刚好填满"的那一刻
> 就停止了，胸挂之后的**背包连碰都没碰过**：
>
> ```
> 胸挂 2x2 + 背包 4x2，库存 {鱼·默认: 10}（2x2 的鱼）
> 正确：胸挂 1 条 + 背包 2 条 = 3 条 / 300
> 错误：1 条 / 100，而且照样报 OPTIMAL
> ```
>
> 这个 bug 能躲过所有随机对拍（随机小网格里两个容器往往同时关注），
> 是被 `test_packing.py::test_multi_container` 这个**手写的两容器用例**抓住的。
> 审计建议：容器推进这类"路径分叉"逻辑，务必保留**手写的最小多容器用例**，
> 不要只依赖随机对拍。

### 3.5b 三个出口必须同量纲（`gained` 的语义）

搜索在若干处"提前收工"，**所有出口必须返回同一量纲的分数**，否则不同路径的
分数不可比，父状态会选出错误的分支。当前出口如下：

| 出口 | 条件 | 返回 |
|---|---|---|
| 无容器 | `ri >= len(regions)` | `gained` |
| 件数用尽 | `left == 0` | `gained` |
| 容器已满 | `free_n == 0` | **继续下一个容器**（见 §3.5） |
| 分支不可行 | 价值上界 < `min_value` | `0`（只在"价值是硬约束"时启用） |
| 预算耗尽 | `stats["stop"]` | `0` |

`gained` 的含义是**「从当前状态起，最优子方案能贡献的 objective 分数」**，
且与 objective 一致：

* `value` 目标 —— 真实价格之和；
* `cells` 目标 —— $\text{BASE}\times(\text{放的件数}) - (\text{占格})$。

> **反面教材**：曾经让"容器已满"这一出口返回 `gained + BASE`（想把"本容器
> 还能再塞一件"算进去）。这在 2x2 容器装完一条 2x2 鱼之后就凭空多出一个
> `BASE`，因为"还剩 3 个自由格"并不代表"还能再放一件 4 格的鱼"。
> 于是"真实的放置路径"分数反而低于"什么都不放"的路径，搜索报 INFEASIBLE。
> **教训**：凡是"从某状态直接返回"的出口，其返回值的量纲必须与递归返回值
> 严格一致；任何"顺手加一点"的补偿都会破坏可比性。

### 3.5c 硬约束必须进入**状态比较**，而不只是剪枝（`cells` 目标的第二个坑）

`cells` 目标的得分 $=\text{BASE}-\text{占格}$，**与价格无关**。因此"得分最高"
的那条路径完全可能是一条**不达标**的路径：

```
容器 4x4，库存 {1x1/900, 2x3/3000}，目标 1000，限 1 件
 分支 A：放 1x1/900   -> 占 1 格，得分 BASE-1   ← 分数更高
 分支 B：放 2x3/3000  -> 占 6 格，得分 BASE-6   ← 真正可行
```

若父状态只比得分，它会留下 A；随后 A 因价值不足被判不可行，整个实例被报成
`INFEASIBLE`，回本求解只能退回"未证明"的贪心解。修复方式：

1. 递归**额外返回累计价值** `value`（不能事后用价格反推，因为 cells 得分里
   根本没有价格）；
2. 有硬约束时用字典序比较器：

```python
def _better(v_a, s_a, c_a, v_b, s_b, c_b):
    if min_value:                      # 价值是硬约束
        a_ok, b_ok = v_a >= min_value, v_b >= min_value
        if a_ok != b_ok:
            return a_ok                # 达标的方案才可能是答案
        if a_ok:                       # 两边都达标 -> 比客观目标
            return c_a < c_b           #   cells：占格少者胜
        return s_a > s_b               # 两边都不达标 -> 只给搜索一个方向
    return s_a > s_b                   # 无硬约束 -> 纯 objective
```

> **反向也踩过一次**：只加"价值上界剪枝"、不改比较器是不够的 ——
> 那个 bug 的根因在**比较**，不在剪枝。上界剪枝仍然需要（它能让不可行分支
> 更早死掉），但它不改变"父状态留下谁"。

### 3.6 记忆化

```python
memo[(objective, ri, occ, rem, left)] = (best_score, best_placements, best_value)
```

同一个「已占格位图」无论通过什么顺序到达，都命中同一缓存项。
这正是填充序策略带来的好处 —— 它把「放置顺序」这个自由度**归一化掉了**，
否则同一组放置会产生 $|\text{放置}|!$ 个等价状态。

> **前提**：记忆化只在「缓存值 = 该状态的完整子树真值」时才是正确的。
> 这要求搜索中**不能有依赖上下文的剪枝**。§13 会讲到我如何违反了这个前提 ——
> 因此凡是被"依赖上下文"剪掉的分支（价值上界剪枝、cells incumbent 剪枝、
> `stats["stop"]` 提前收工）都**只返回不落缓存**，避免把不完整的真值写进 memo。

### 3.7 开解预热（incumbent）

DFS 之前先用**全局最佳优先贪心**跑一遍：

```python
while True:
    在 所有容器 × 所有款式 × 所有可放位置 里选出当前目标下最好的一个
    （value 目标用 价值/格数；cells 目标偏好占格少的小件；平手偏好大件）
    放下它；没有可放的就结束
```

必须是**全局**最佳优先：早期版本写成"按款式顺序逐轮扫一遍"，某个款式在
当前位置放不下就跳过，很容易卡在极差的解上（实测出现过"胸挂完全空着、
背包只用一半"）。

贪心解作为 incumbent 使用，并且在**预算耗尽**时是最终返回的兜底解。
三处关键细节：

1. **耗时不计入搜索预算**。`deadline` 必须在贪心**结束之后**才开始计时。
   早期写成"函数入口 + 预算"，于是在款式多的大实例上贪心就把预算吃光，
   搜索第一次展开节点就撞上过期 deadline 立刻停摆 —— 表现是"搜索明明该找到
   解却返回空"，只能退回未证明的贪心解，`exact` 标记大面积失真。
2. **空的贪心 = 没有达标 incumbent**。贪心构造后立即做 `min_value` 校验，
   不达标就清空成 `[]`。cells 模式的 incumbent 剪枝因此也必须以
   `greedy != []` 为前提 —— 否则阈值来自一个"占格少但不达标"的方案，
   会把合法的达标分支成片剪掉。
3. **兜底比较必须按真实目标比**。搜索超时后用谁的解，判据是
   `(价值, -件数)` 的字典序（value 目标先比价值），**不能只比件数**：
   早期写成"贪心件数更少就用贪心"，结果用一个"少一件、总价更低"的方案
   把价值换掉了 —— 实测满仓实例从 1950 掉到 1390。

> ⚠️ 同理，**绝不能**拿 `BASE*件数 - 占格` 这个内部得分去比较"搜索解 vs
> 贪心解"：两者件数不同，而分数里每件都带一个巨大的 `BASE`，会让"多装几件"
> 凭空赢过"占格更少"。该得分只用于**剪枝阈值**，不用于最终挑选。

## 4. 快速通道（`pack(fast=True)`，默认开启）

### 4.1 动机

实测（§6）：**不限供给**场景下，69 格 + 63 款式跑 105 秒 / 680 万节点才证出最优。
而 UI 每次重算都要用它。所以需要一条「能立刻断定最优」的快路径。

### 4.2 分数背包上界

$$\text{UB}_{\text{frac}}(s) = \max_{\text{允许分数}} \sum_i \frac{v_i}{\text{cells}_i} \cdot \text{area}_i
\quad \text{s.t.} \sum \text{area}_i \le s$$

实现：按密度降序**整件**装填，最后一件允许分数。

```python
for s in range(1, capacity + 1):
    frac, left = 0, s
    for k, vi in enumerate(order):        # order = 按密度降序
        v = variants[vi]
        if v.cells <= left:
            n = left // v.cells           # 整件装，不出现分数
            frac += n * v.price
            left -= n * v.cells
        if left > 0 and maxd[k] > 0:
            frac += int(maxd[k] * left)   # 余数按分数（唯一的松弛）
            left = 0
    table[s] = frac
```

> **⚠️ 这里踩过一个概念性陷阱**：为收紧「容量不被最优物品整除」时的界，
> 我曾额外算一个候选「只用某一种物品能把 $s$ 格装出多少」再取 **min**。
> 这是**错的** —— 「只用一种」是**下界**性质的值，$\min(\text{上界}, \text{下界})$
> 可能远低于真实最优。详见 §13.2。
>
> 正确做法：**只有所有候选都是真上界时才允许取 min。** 现在的实现只有一种候选。

### 4.3 快通道判定

```python
if fast and stock is None:
    if greedy_value >= fractional_bound(total_capacity):
        return PackResult(..., optimal=True, nodes=0)     # 跳过搜索
```

贪心值 ≥ 上界 $\Rightarrow$ 贪心即最优（因为上界不小于任何可行解）。**这个推理是严格的。**

已验证（`tools/audit_claims.py` 的 D 项）：在「4×2 容器 + 1×1/2×2 两种鱼」这类
上界可达的实例上，快通道触发、`value == 上界 == 暴力枚举真值`。

### 4.4 快通道**失效**的场景（已知未解）

实测（真实数据，69 格，最高密度 1900/格＝2 格装）：

```
真实最优（整数解）  = 130160     34 条 2 格 @3800  = 129200   →  68 格
                                1 条 1 格 @960   =    960   →  69 格满
                                ----------------------------
                                合计 = 130160

分数背包上界        = 131100     34×3800 + 1×1900(分数) = 129200 + 1900

                    gap = 940   ← 来自那 1 个"分数格"：
                                  上界假设余下 1 格也能按 1900/格 计，
                                  而实际最小的鱼是 1 格 960。
```

上界 131100 > 真实最优 130160，快通道**不触发**，退化为完整搜索。

> 这里 1900 是"每格"密度，`1×1900 = 1900` 是那 1 格的**分数**贡献；
> 而 960 才是 1 格鱼的真实售价。两者相差 940，正是 gap 的来源。

## 5. 布局来源：搜索**直接产出坐标**（既不是二次重摆，也不是回放）

### 5.1 曾经的缺陷（第三方审计确认，已修复）

原实现是：

```
DFS 求最优 counts  →  丢掉坐标  →  用「大件优先 + 首次适应」重摆一遍
```

审计指出这一步**没有完备性保证**：counts 有解，但重摆可能失败，
于是程序会报告一个"最高价值"却给不出能实现它的布局。这是**算法本身会错**，
比"缺一个形式化证明"严重得多。

> **审计给出的具体反例不成立，但它的推理方向是对的。**
> 审计的反例是 4×4 容器 + A=2×3, B=1×4, C=3×1。我实测**旧实现能摆出来**
> （`A@(0,0) 2x3, B@(2,0) 1x4, C@(3,0) 1x3`——注意 C 旋转了，
> 审计假设 C 不能旋转，而本实现允许旋转，所以它的反例在允许旋转时失效）。
> 但这**不构成辩护**：一个反例失效 ≠ 算法安全。我改用穷尽方式判定（见 5.4），
> 并直接换掉了这个不可靠的环节。

### 5.2 现在的做法：搜索**直接产出坐标**（不做任何回放）

`_replay_optimal()` 已经被**删除**。现在 `solve()` 的返回值就是
**`(得分, 该状态的放置列表, 该路径的累计价值)`** —— 放置列表是在递归
返回时就地拼出来的：

```python
best_list = [Placement(container_index=ri, fish_name=v.name,
                       x=x0, y=y0, w=v.w, h=v.h, price=v.price,
                       shape_index=vi)] + sub_list
```

关键性质：

* 「搜索证明的东西」与「返回的布局」是**同一个对象**，不存在两次独立计算
  之间产生分歧的可能 —— 这比"回放时逐格复核"更根本；
* 不需要任何事后启发式摆放，也不需要在 memo 里额外存分支掩码；
* `Placement` 里带 `shape_index`，能精确复原当时选的是哪个朝向。

> 为什么删掉回放：回放的正确性依赖"记录的掩码"与"重走的坐标"一致，
> 而 `memo` 的键在不同目标下会被复用，审计曾指出这里存在静默错位的风险。
> 直接产出坐标从根上消除了这一类问题，代码也少了一整块。

### 5.3 为什么这样就没有"重建"问题了

因为**没有重建这一步**了。「搜索证明的价值」与「返回的布局」是同一个对象，
而不是两次独立计算的产物。测试上体现为一条强不变量：

```python
sum(p.price for p in res.placements) == res.value
```

以及逐格校验：不重叠、不出界、只落在 mask 的可用格上。

### 5.4 覆盖到哪一层（`tools/stress_reconstruct.py`）

拆成两类目标，避免一个循环又慢又难定位：

| 类 | 次数 | 检查内容 |
|---|---|---|
| A 不变量 | 2000 | 布局合法、布局价值 == value、件数 == len(placements)、不超库存、`optimal` 与 `termination` 一致 |
| B 最优性对拍 | 400 | **暴力枚举真值 == 求解器 value == 布局实现的价值** |

B 类刻意放在小容器（≤4×4）上，因为要对拍暴力真值。
它正是旧实现会露馅的地方：若 counts → 布局有信息损失，
"布局实现的价值"就会小于报告值，B 类立刻报错。

实测结果（`python tools/stress_reconstruct.py --quick` 可快速复跑）：

```
A. 不变量检查 2000 次 -> 异常 0
B. 最优性对拍  400 次 -> 异常 0
```

> **仍未覆盖的**：真实尺寸容器（如 5×9）上的"最优布局 vs 另一个同样最优的布局"
> 不可比，因为一条实例可能有多个最优布局。这里只断言价值与合法性，不断言唯一性。

## 7. 正确性验证手段

### 7.1 暴力枚举对拍（`test_packing.py::test_matches_bruteforce`）

对**小网格随机实例**，用独立实现的暴力枚举（枚举放置集合的所有子集）算真值，
与 B&B 结果逐一对拍：

```python
for trial in range(40):
    w, h = rng.randint(2,5), rng.randint(2,4)
    c = Container(f"t{w}x{h}", "背包", w, h)
    types = rng.sample(catalogue, rng.randint(2,4))

## 8. 与参考意见的逐条对照

| 参考意见 | 本实现 | 说明 |
|---|---|---|
| 建模为 2D Knapsack + Rectangle Packing | ✅ 一致 | |
| 有限数量展开成独立 0/1 实例 | ✅ 一致 | 用计数向量而非显式展开，语义等价、状态更少 |
| 用 CP-SAT 求精确解 | ❌ 未采用 | 见 §2；本实现用完备 DFS，同样精确（在跑完时） |
| `AddNoOverlap2D` / 四向析取 | ✅ 等价（位掩码与运算） | 参考意见的析取写法需注意 bilinear 问题，见 §2.1 |
| 旋转用 `rotation = 0/1` | ✅ 一致 | 预生成两个朝向作为独立候选 |
| 「回本」不需另写算法 | ⚠️ **部分分歧** | 见 §8.1 |
| 最大价值 / 最低回本 / 是否回本 三输出 | ✅ 已实现 | `plan_run()` 返回 `ceiling` / `break_even` / `can_break_even` |
| 建议封装成 `optimize_fish_packing(...)` 接口 | ✅ 已有等价接口 | `plan_run()` / `report_catch()` / `pack_containers()` |
| 「不要让 UI 理解装箱算法」 | ✅ 一致 | UI 只消费 `(x, y, w, h)` |

### 8.1 与参考意见的**实质性分歧**：回本方案的目标函数

参考意见主张：**最低回本 = $\min \sum v_i$ s.t. $\sum v_i \ge \text{cost}$**，
即「最小化总价值但仍 ≥ 成本」。

我认为这个目标函数**在业务上不成立**：

> 钓到鱼是**免费且已经发生**的。你不可能「选择只钓一条 3100 的鱼」——
> 你钓到什么就是什么。所以「最小价值组合」不是玩家能执行的策略。

本实现改用的目标：

$$\min \;(\text{条数}, \text{总占格}) \quad \text{s.t.} \quad \sum v_i \ge \text{cost}$$

即「**最少几条、最少占几格就能回本**」。理由：玩家真正的决策是
「再钓几条才能回本、还要留多少格子给别的收益」。
同条数时按占格做次级排序（例如铂金银龙鱼两个款式同价 3200，选 1×2 而非 1×3）。

**这个分歧值得审计** —— 若认为应同时提供两种口径，实现成本很低
（把 DP 的目标函数换成 $\min v$ 即可）。

## 9. 已知缺陷与未解问题

### 9.1 超容量场景需要百秒才能证明最优 🔴

如 §6.2：108 格库存 / 69 格容量时，**无剪枝的完整搜索要 105 秒 / 680 万节点**。
默认 3 秒预算只能给次优解（但如实标 `optimal=False`）。

### 9.2 「不限供给」路径的指数爆炸 🔴

`stock=None` 时 `max_per_type` 被设为 `total_capacity // cells`（可达 34），
`rem` 向量空间巨大，记忆化几乎无效。
快通道在「容量不被最优格数整除」时失效（§4.4），此时退化为完整搜索。

### 9.3 回本组合的精确性 ✅（本轮已严格化）

**当前状态**：回本组合不再来自 DP。`plan_run` 直接调用
`Packer.solve_break_even`，对

```
minimize (条数, 占格)   s.t.   价值 ≥ 回本线, 可装下
```

做**严格词典序**优化，由 §15.7 记录的 120 组暴力对拍验证。
`RunPlan.break_even_exact` 如实报告是否证明了最优，UI 的措辞随之切换
（证明不了就**不写**"理论最少"）。

DP（`_dp_min_combo`）**仍然存在，但只提供件数下界**（`lower_bound`），
用于让第 1 阶段跳过理论上不可能达标的件数；它**再也不是答案的来源**。

**历史留档**：早期版本的 DP 只按**总格数**约束、不感知形状，事后用
`Packer` 复核可装性，复核失败只发警告而不回溯 —— 那确实不是精确算法，
第三方审计把它从 🟡 升为 🔴 是对的。现在这条路径退化为
「精确求解未能给出可行解时的最后兜底」，并会被 `break_even_exact=False`
如实暴露。

### 9.4 重建无形式化保证 ✅（本轮已彻底消除）

见 §5.1 / §5.2。**"重建/回放"这个环节已经被删除**：`solve()` 直接返回
放置列表，"搜索证明的东西"与"返回的布局"是同一个对象。因此这条缺口
不再存在 —— 现在只剩运行时不变式（`stress_reconstruct.py` 的 2000 组）
与 400 组暴力对拍作为证据。

### 9.5 容器优先级的语义尚未定死 🟡

现在是「先填满胸挂，再填背包」。**这句话必须被精确定义**，因为三种含义截然不同：

| 语义 | 含义 | 对最优性的影响 |
|---|---|---|
| **A. 硬约束** | 只要某件能放胸挂，就必须放胸挂 | 是问题定义的一部分，最优性相对该定义成立 |
| **B. 词典序第二目标** | 先最大化总价值；总价值相同时最大化胸挂利用率 | 仍是精确优化，但目标函数变成二元组 |
| **C. 搜索顺序** | 只是先尝试胸挂，允许求解器为了更高价值而改用背包 | 对最优性**无影响**，纯启发式 |

**当前实现是 A（硬约束）**：容器按序处理，前一个装完才动下一个。
这**不是"次优算法"**，而是问题定义 —— 但也意味着它**不追求跨容器的最优分配**。
举例：某条鱼放背包更省空间、从而能多装一条别的鱼，当前实现不会去做这种交换。

若要改成 B（更贴近"胸挂优先但价值优先"的业务直觉），需要：
先把目标改为 $\max(\text{value}, \text{chest\_usage})$ 的词典序，
即先求最优 value，再在 value 相同的解集里最大化胸挂占用 ——
**不能用 `value + ε·chest_usage` 近似**，因为 ε 难以取到"绝不改变主目标"的量级。

### 9.6 `optimal` 的语义边界 ⚪（已改进）

原本只有 `optimal: bool`。第三方审计指出这不足以表达真实情况
（尤其是我已经历过"错误剪枝 → 19380 → `optimal=True`"）。
现在改为 `termination` 状态：

| 值 | 含义 |
|---|---|
| `OPTIMAL` | 搜索完整跑完，最优性得到证明 |
| `TIME_LIMIT` | 触预算：拿到了可行解，**但不保证最优** |
| `NO_SOLUTION` | 触预算且一件都没放下 |
| `EMPTY` | 无事可做（没有容器或没有候选） |

`optimal` 保留为**计算属性** `termination == OPTIMAL`，
这样它不可能与 `termination` 不一致 —— 而那种不一致正是被撤销的剪枝 bug 得以隐藏的方式。

## 10. 如果要迁移到 CP-SAT，需要保持的语义

1. **容器格位图**：用 `place[i][k][x][y][r]` 布尔变量，只对
   「该放置完全落在 $R_k$ 可用格内」的组合生成。**不要用连续矩形假设。**
2. **槽位互斥**：对 $R_k$ 的每个可用格 $g$，
   $\sum_{\text{覆盖 } g \text{ 的放置}} \le 1$。比四向析取更紧且线性。
3. **数量约束**：$\sum_{k,x,y,r} \text{place}[i][k][x][y][r] \le n_i$。
4. **容器优先级**（若保留）：加权重 $\varepsilon$ 鼓励先用胸挂，或显式分阶段求解。
5. **三输出**：① $\max \sum v$；② $\min$ 条数 s.t. $\sum v \ge \text{cost}$；③ 可行性。
6. **性能目标**：不限供给场景毫秒级返回；有限供给已满足。
7. **必须保持的既有语义**：
   - 同价时优先占格更小的款式
   - 价格 0 的款式视为未填写、必须排除
   - `rotate` 可配（允许/禁止旋转）

## 13. ★ 失败的剪枝实验（本次最重要的发现）

### 13.1 动机与做法

§9.1 说超容量场景要 105 秒才能证明最优，根源是**搜索里完全没有剪枝**。
我去加了剪枝，做法是：

```python
# 预计算上界表 UB[s] = 用 s 个格子最多能装出的价值（忽略形状）
# 搜索中：
stock_value = Σ 剩余数量 × 该鱼种最高单价
ub = min(UB[free_cells], stock_value)
if current_value + ub < 已知最好解:
    剪掉这一支
```

用**静态**阈值（贪心开解的价值）而非动态最优，是为了不污染记忆化缓存
（缓存值必须是「该状态完整子树的真值」）。

### 13.2 结果：剪掉了真最优，还谎称最优

```
带剪枝  : value=19380  optimal=True   nodes=4,531     耗时 0.03s
无剪枝  : value=19880  optimal=True   nodes=6,839,496 耗时 105.7s
```

**剪枝把真实最优 19880 剪成了 19380，却仍然标记 `optimal=True`。**
这是最危险的一类缺陷 —— 静默给出错误答案，还自称已证明最优。

### 13.3 揭穿它的方法（值得复用）

不靠读代码，靠**独立的可行性校验**：

```bash
python tools/verify_value_feasible.py
```

它手工贪心构造一个 19800 的摆法并逐格校验，证明「高于 19380 的解确实存在」，
从而反证剪枝无效：

```
求解器结果: value=19380 optimal=True used=66
独立重建:   value=19380 无重叠且在界内=True   [OK] 求解器报告的 value 是可实现的
试着构造更高价值的组合:
   全部石斑鱼、去掉罗非鱼: 想要 21080 (84 格) -> 实际装下 19800 (68 格) 合法=True
```

**教训**：`optimal=True` 这个自述标志不能用来验证自己。
必须有**外部**手段证明「更高的解存在」或「更高的解不存在」。

### 13.4 根因（**已按第三方审计意见修正**）

> ⚠️ **本节原先的结论是错的，已撤回。** 我原来写的是「多容器下
> `UB(free_cells)` 与 `stock_value` 的组合不是有效上界」。
> 第三方审计指出这个数学判断有误，**我复核后确认审计正确，是我的错**。
> 修正如下。

**根因 1（确认无误）：对"下界性质"的候选取了 min。**

我曾为收紧界，额外算了候选「只用某一种物品能把 $s$ 格装出多少」，再与密度贪心取 min。
这是**错的**：

```
s = 4，目录 = {2格3800, 2格20}
  密度贪心:      frac = 7600
  只用某种鱼:    2×20 = 40
  min → 40        ← 一个远低于真值(7600)的数，被当成"上界"
```

$\min(\text{上界}, \text{下界})$ **不是**上界。
**规则：只有所有候选都被证明是真上界时，才允许取 min。**
$\min(\text{上界}, \text{上界})$ 才是合法的。

**根因 2（已修正）：不是"无效"，而是"过松"，且我的实现另有 bug。**

原结论撤回。正确的推理是：

$$\text{真实解} \Rightarrow \Delta \le UB_{\text{area}}(free\_cells) \quad\checkmark$$
$$\text{真实解} \Rightarrow \Delta \le stock\_value \quad\checkmark$$
$$\text{两者都是上界} \Rightarrow \Delta \le \min(UB_{\text{area}}, stock\_value) \quad\checkmark$$

放松约束只会让可行域**变大**：忽略几何、忽略洞、忽略容器边界、忽略顺序、
把可用格数合并成一个总面积容量……**每一项都是额外限制，去掉它们得到的值只会更高。**
所以分数背包在「总可用格数」口径下是标准 relaxation，**是真上界**；
`stock_value`（剩余数量的最大可能售价）同样是真上界。多容器不破坏这一点。

**那么剪枝为什么还是错了？** 答案是：**我的实现里有 bug，不是数学不成立。**

我当时的第二次修复（去掉 min、改用 `min(UB_table[free], stock_value)`）
在实测中仍然把 19880 剪成 19380，说明代码与我以为写下的逻辑不一致。
**我当时没有继续查代码，而是把锅甩给了数学** —— 这是不严谨的，也是这次审计
最有价值的一条批评。因此本文档现在明确记：

> 剪枝失效的**根因 2 是"实现 bug（未定位）"**，不是"上界无效"。
> 该 bug 已随剪枝一起撤销，**仍未定位**。重新引入剪枝时必须重新排查。

### 13.5 当前状态与重新引入剪枝的前提

**剪枝已从代码中移除**，`packing.py` 里留了显著注释说明为什么。
上界表 `_bound_table()` 保留，但**只用于不限供给的快通道** ——
那里只用「贪心值 ≥ 上界 ⇒ 贪心最优」这一个方向的推断，
界偏大只会导致快通道不触发（退化为完整搜索），**不会造成错误答案**。

若要重新引入搜索内剪枝，**前置条件**：

1. 先复现并定位第 13.4 节那条"实现 bug" —— 在界被证明有效之后，
   错误只可能出在实现里，不要再怀疑数学；
2. 新增回归测试：**同一实例下「有剪枝」与「无剪枝」的结果必须逐位一致**
   （小实例必须 `TERMINATION == OPTIMAL` 且 value 相同）；
3. 用 `verify_value_feasible.py` 对剪枝后的结果做独立可行性校验；
4. 只要剪枝可能影响完备性，就**不准**标 `OPTIMAL`；
5. 可以按审计建议把界换成 **Fractional Bounded Knapsack**
   （把剩余数量也纳入分数背包），这比"不限供给上界 ∩ stock_value"通常更紧，
   且仍然是真上界。

### 13.6 这次实验的净收益

剪枝本身失败了，但留下了三样有用的东西：

- `tools/verify_value_feasible.py` —— 独立可行性裁判，能揭穿「自称最优」的假象
- `tools/audit_claims.py` 的 C 项 —— 上界 vs 可达最优的自动化校验
- 本文档 §13 —— 把剪枝失效的教训与**我犯的推理错误**一同固化下来

**并确认了一条重要事实**：求解器在**不剪枝**时的答案是正确的
（19880 = 真最优，105 秒证出）；问题只在速度，不在正确性。

## 15. 本轮修复记录（5 个真实 bug 的定位过程）

本轮的目标是把回本求解收口成严格的词典序优化
`minimize (条数, 占格) s.t. 价值 ≥ 目标`。实现过程中，先在**已有代码**里
挖出 4 个此前一直存在、并且都成功绕过了随机对拍的 bug；第 5 个是本轮新引入
又被立刻抓回的。全部记录如下，附**可复现的判据**。

### 15.1 致命 bug：容器填满后**直接收工**，不进入下一个容器

| 项 | 内容 |
|---|---|
| 现象 | 胸挂 2x2 + 背包 4x2，2x2 的鱼：只装出 1 条 / 100，期望 3 条 / 300 |
| 而且 | `termination == OPTIMAL` —— 完全错误却自称最优 |
| 根因 | `if free_n == 0: return gained`。`occ` 是**容器局部**掩码，填满只代表本容器结束；直接 return 让背包从未被访问 |
| 抓到它的测试 | `test_packing.py::test_multi_container`（**手写**的最小两容器用例） |
| 为什么随机对拍漏了 | 随机小网格里两个容器经常能同时被同一个分支覆盖，差异被掩盖 |
| 修复 | `return solve(ri + 1, 0, rem, left, gained, value)` |

**教训**：随机对拍只能证明"没有随机可发现的错"，**不能替代手写的最小语义用例**。
多容器、多目标、空库存、恰好装满 —— 这类"路径分叉"场景必须各留一个手写用例。

### 15.2 与 15.1 同源的错误早退："剩余库存都放不下就收工"

```python
# ❌ 曾经的写法
if free_n == 0 or not any(rem[slot] > 0 and v.cells <= free_n for v in variants):
    return gained
```

看着像"库里没东西装得下就没什么可搜的"，但**自由格是离散的**：

> 2x2 的胸挂放了一件 2x2 的鱼 → 还剩 **3** 个自由格 → 一条 **1x1** 的鱼
> 明明还能放进去。而 `3 < 4` 会让整个分支在**根上**就被剪掉。

这一条与 15.1 叠加，正是"胸挂装满、背包全空"的直接来源。

**修复**：删掉这条早退。它本来就是**多余**的 —— 正确性由锚点枚举保证：
锚点是**最左上**的自由格，覆盖它的矩形就是全部候选；一个都放不下时，
循环自然什么都不产生。

> **判据（可复用）**：任何形如 `if <某局部量> < <某件物品需求>: 放弃整支`
> 的剪枝，都要先问一句：**这个局部量是"剩余容量"还是"剩余连通自由格"？**
> 二维装箱里这两者**不等价**，用错的每一次都是静默丢解。

### 15.3 出口量纲不一致：凭空多出的 `BASE`

§3.5b。cells 目标的得分里每件都带 `+BASE`。曾经让"容器已满"这一出口返回
`gained + BASE`，等于宣称"还剩 3 个自由格 ⇒ 还能再放一件"。后果是
"真实放置路径"的分数反而低于"什么都不放"的路径，搜索报 INFEASIBLE。

**修复**：所有出口统一返回 `gained`；`free_n == 0` 明确改为"推进容器"。

### 15.4 `cells` 目标的硬约束没有进入状态比较

§3.5c。这是**本轮新引入**的 bug：为了让 `min_value` 成为真正的硬约束，
我加了"价值上界剪枝"，但**比较器**仍然只比 cells 得分，于是
"1 件 1x1 / 900（占 1 格，不达标）"战胜了
"1 件 2x3 / 3000（占 6 格，达标）"，整个实例被报成 INFEASIBLE。

**修复**：递归额外返回累计价值，比较器改为"达标的优先，其次才比 objective"。

> **特别注意**：累计价值**不能**用价格和事后反推 —— 必须由递归带着走。
> 中途我写成 `cand_value = value + v.price + sub_value`（子调用已经加过
> `v.price`），把价值记了两遍，900 变成 1800，把"不达标"判成了"达标"。
> **单一事实来源**这条规则在"递归返回多个量"时特别容易被违反。

### 15.5 兜底比较用错了目标

搜索超时后要在"搜索解"与"贪心解"之间选一个。早期判据是
「贪心件数更少就用贪心」，结果是用一个"少一件、总价更低"的方案
把价值换掉了 —— 实测满仓实例从 **1950 掉到 1390**。

**修复**：判据改为 `(价值, -件数)` 字典序，先比真实目标。

> 与此同源的另一条：**绝不要**用 `BASE*件数 - 占格` 这个内部得分去比较
> 两个件数不同的方案 —— `BASE` 的权重会让"多装几件"凭空赢过"占格更少"。
> 该得分只允许出现在**剪枝阈值**的语境里（那里比较的是"同一状态的路径分数"）。
